# Samsung UE49NU8079 adaptation

This is the detailed device record for this fork. See [TV status](tv-status.md) for the short current summary and the distinction from the upstream LS03D.

This fork records an owner's tested adaptation of CleanFrame for a Samsung
UE49NU8079, firmware **T-KTM2DEUC-1360.0**, Tizen **4.0**, ARMv7.
Observations below were collected on 29–30 October 2026. They are not a claim of
support for every NU8000 or Tizen 4 TV.

The TV-specific adaptation is an explicit build overlay. The source identity
checks and Tizen 6.5 package declaration remain unchanged; this fork also adds
the configurable [Sources menu](sources.md) in `app/`. Run the separate
builder below to reproduce the adapted package. Ordinary `npm run package`
does not apply this overlay.

## Changes captured

- Generated manifest requests Tizen 4.0 and the owner's own SDK application identity.
- Sources replaces the former direct Live TV control. Its Live TV item selects
  the reported tuner before launching `org.tizen.tv-viewer` for cable TV.
- Prime Video uses the installed `evKhCgZelL.AmazonIgnitionLauncher2` target.
- YouTube keeps its catalogue/preference ID, but the overlay routes launches
  of `9Ur5IzDKqV.TizenYouTube` to the installed `com.samsung.tv.cobalt-yt` entry.
  This also applies after refreshing All apps; saved app choices are unchanged.
- Samsung Home keeps `com.samsung.tv.csfs`; error guidance names Samsung Home.
- An optional local app selection is seeded only when neither current nor legacy
  CleanFrame preferences exist. Updates preserve the saved order and appearance.
- Only public fonts are packaged. Signing and installation remain separate steps.
- TV settings uses an explicit Tizen Settings app control addressed to
  `org.tizen.menu`; a plain application launch caused the focus defect below.

## Home and fixed-startup investigation, 31 October 2026

The requested behaviour is both physical Home returning to CleanFrame and
power-on showing CleanFrame regardless of the previously used app. Standby/wake,
full restart and physical AC cold start require separate observations.

The authorised read-only checks used the existing Samsung SDB 4.2.36 client.
The TV reported Tizen 4.0, ARMv7, sdbd 2.2.31 and plugin `3.4.1_TV_REL`.
`intershell_support`, `sdbd_rootperm`, `rootonoff_support` and `appcmd_support`
were disabled; `filesync_support` was `push`. The expected CleanFrame identity
was present in `0 applist`. Plain `id` and
`vconftool get db/appfw/home_appid` returned `closed` with exit code 1.
HTTP model information matched UE49NU8079, but its firmware field was `Unknown`.
The previously recorded 1360.0 version was not independently re-read in this session.

No device upload, package installation, app launch, reboot, root acquisition or
native setting write was performed. Native Home/startup values and a recovery
baseline have not been obtained. Private probe source and command results are
kept under ignored `.local/native-home-investigation/`.

The ordinary shell result does not test the separate package-name execution
workaround described in the [original advisory](https://bishopfox.com/blog/samsung-tizen-os-version-through-9-0).
A bounded SDK-only marker/identity/timing probe was subsequently executed after
the owner explicitly authorised that command-injection technique. No package
was uploaded: a unique nonexistent package name was used. The fixed commands
requested a marker and user identity, a no-op, and a two-second delay. No root
acquisition, native API setter or filesystem-writing payload was attempted.

| Probe through Windows SDB 4.2.36 | Result | Elapsed |
| --- | --- | --- |
| Ordinary nonexistent-package control | Installer responded `Package not found [-5]` | 0.195 s |
| Encoded marker and identity | `closed`, exit 1, no marker/identity | 0.067 s |
| Encoded no-op control | `closed`, exit 1 | 0.063 s |
| Encoded two-second delay | `closed`, exit 1 | 0.083 s |

The delay delta was approximately 0.020 s, not two seconds. The tested CLI
invocation therefore did not establish SDK command execution. No native
Home/startup values were read. Subsequent HTTP and SDB app-list checks succeeded;
the installed-app list matched the pre-probe list and retained CleanFrame.
These checks do not establish visible TV behaviour.

A [different-model Windows report](https://github.com/chris-ritsen/samsung-tv-root/issues/23)
describes CLI failure but successful direct SDB framing. The owner separately
authorised testing that transport on this TV. A minimal Python client used
CNXN/OPEN/OKAY/WRTE/CLSE framing reviewed against
[the published direct transport](https://github.com/invaliddayta/samsung-tv-tools/blob/1974b5dfbfd2f8f04dfddbec3a94570b398a1d46/tools/tv_access/sdb_direct.py).
The root bootstrap, uploads and arbitrary-command interface were not included.
Offline packet checks covered checksums, size bounds and truncated streams.

The PC's SDB connection to this TV was disconnected for the test and restored
afterward. Every direct handshake succeeded. Direct `shell:0 applist` returned
the expected CleanFrame identity; the ordinary nonexistent-package control
returned the installer's `Package not found [-5]` response.

| Direct-SDB request | Wire response | Time after OPEN |
| --- | --- | --- |
| Marker and identity | Immediate CLSE, no output or OKAY | 0.0195 s |
| No-op control | Immediate CLSE, no output or OKAY | 0.0209 s |
| Two-second delay | Immediate CLSE, no output or OKAY | 0.0215 s |

The delay difference was only 0.0006 s. Thus this exact package-name execution
probe did not establish command execution even without the Windows CLI; the
failure is not solely a CLI argument/framing issue. A CLSE packet alone is not
proof of rejection, but neither the marker nor the delay established execution.
No alternative payload sweep or root route was attempted. The native Home/startup
getter and recovery baseline remain unavailable through the tested paths.

The final ordinary SDB connection succeeded, and the installed-app list exactly
matched the list taken before the direct test. No package was uploaded, no app
was launched, no restart was requested and no Home/startup setter was invoked.
Private source, packet summaries and post-checks are in
`.local/native-home-investigation/direct-20261031T072819Z/` and the adjacent
`direct-probe.py`. This result does not prove all possible access paths fail.

Relevant external evidence, not results on this TV:

  `startup_appid` alone was reset at reboot; its Home-app plus autostart method

## Offline firmware analysis with REA, 31 October 2026

The owner rejected external network automation and authorised local firmware
analysis. REA and supplementary source checkouts were placed under the requested
IdeaProjects directory. No branch was created and no TV access was used for this
phase. Linux tools ran in a Docker container on the existing WSL2 backend;
analysis containers had networking disabled and no access to TV devices.

The [Samsung support listing](https://www.samsung.com/hu/support/model/UE49NU8079TXZG/)
provided a still-working official download of **T-KTM2DEUC 1360.0**, dated
1 April 2026 inside `info.txt`. The ZIP contains an encrypted MSDU11 image.
The image's MD5 matched `info.txt`; ZIP reads passed CRC checks. Source URLs,
SHA-256 digests and the original files are retained in ignored
`.local/native-home-investigation/firmware-1360/`.

Offline decryption with the published
[msddecrypt](https://github.com/bugficks/msddecrypt) implementation succeeded.
The extracted `uImage`, `dtb.bin` and `platform.img` each matched the container's
CRC32. The kernel's own uImage header and payload CRC32 also passed. The kernel
identifies itself as Linux 4.1.10, built 16 January 2026. REA 6.8.0's
`inspect-devicetree` parsed the hardware description as Samsung
SDP1701/Kant-M2. This identifies the downloaded firmware, not a new live-TV
firmware readback.

REA's generic Binwalk/Unblob firmware lane requires additional Linux providers
and limits input files to 128 MiB; it was not used on the 1.38 GB container.
The installed REA 6.8.0 package rejected `uImage` through `inspect-artifact`,
despite newer checkout documentation describing that format. Kernel CRC
validation therefore used an independent local parser. Do not report a
successful REA kernel decompilation or generic firmware scan.

The system image uses VDFS layout 2007. The original
[vdfs-unpack](https://github.com/gtors/vdfs-unpack) decoder produced errors and
could truncate authenticated compressed files. A separate local source copy
was corrected against the extent/hash/signature layout in the published
[VDFS driver](https://github.com/vdfs-team/vdfs4/blob/main/inode.c).
The corrected decoder handles each compressed extent and checks the decoded
file length against the descriptor. A fresh extraction completed with no
reported extraction failures and yielded 38,708 regular files. This is not an
independent verification of every filesystem signature. Original and corrected
logs, source revisions, the local patch and selected files are retained privately.

Static findings:

- **SDB:** `libsdbd_plugin.so` routes shell requests through a command/argument
  parser. Its character validator at ELF address `0x5b9c` rejects, among other
  characters, backticks, `$` and `|`, all present in the earlier fixed probe.
  This supplies a firmware-level explanation consistent with the observed
  immediate closes. `IsDebug` returns false in this release implementation;
  `_getIntershell` delegates to it. No alternative injection was sent to the TV.
- **Home:** `construct_managed_apps` in
  `libapp-context-manager-common.so` calls `vconf_get_str` for
  `db/first_screen/type`, retains the result and uses it to construct the
  `firstscreen` task with `entry_point=smarthub_key` and `source_key` arguments.
  `tvctx-manager` contains the `XF86Home`/`smarthub` key mapping. These are
  concrete code references, but changing that setting to a packaged web app
  has not been tested. The newer helper's `home_appid`/operation-API route must
  not be assumed to apply to this firmware.
- **Startup:** `firstscreen.sh` explicitly launches Samsung's firstscreen app.
  A separate `app-boot-manager` references cold boot, background standby,
  `db/menu/app_booting`, `db/volt/last_service_app_booting` and Smart Hub
  autostart. A Home-target change alone cannot be assumed to pin CleanFrame
  across all power-on modes.
- **Other configuration:** the context manager reads `.app-context.db`,
  including `managed_app`, `key_filter` and `task_filter`. A package-manager
  parser supports `app-context` rules. Public-certificate acceptance, caller
  permissions and suitability for Home/startup remain unverified.
- **USB:** HyperUART scripts configure a `huart0` network interface and start
  the same SDB service. The launcher script requires root and depends on
  additional factory/developer settings. This is evidence of a service path,
  not evidence that an ordinary PC USB cable supplies an unrestricted shell.
  exFAT modules were extracted for possible later comparison; no USB exploit
  compatibility or safe rollback was established.

The firmware includes a .NET 2.0 runtime and `corerun`, so newer .NET 3.1/6.0
helpers cannot be used unchanged. No diagnostic package was built, signed,
installed or launched in this phase. The saved firmware defaults do **not**
replace a live, exact-value recovery baseline. Native Home/startup writes remain
a separate device task requiring that baseline and explicit authority.

### Follow-up: managed getters and manifest rules

REA 6.8.0's `inspect-managed-members` successfully decoded the firmware's
`DotnetPolicyChecker.dll` and `Tizen.TV.System.dll`. The latter's copy in the
policy-checker package is byte-identical to the framework copy. This follow-up
also remained entirely offline.

`Tizen.TV.System.Vconf` exposes managed getters, but this is not an unprivileged
read path. Its static constructor sets `PlatformPrivilege` to
`http://tizen.org/privilege/internal/default/platform`. Both `GetInt` and
`GetString` call `PrivilegeUtil.IsAllowedStatic` before their native getter;
failure throws `MethodAccessException`. The privilege utility reads the current
process SMACK label and UID and calls Cynara. The firmware's core privilege
database also marks this privilege as internal. A public developer signature
does not establish this grant; live behavior has not been tested. Consequently,
no diagnostic app was built or installed on the assumption that this facade
would provide the recovery baseline.

The managed package checker examines assembly and native module references
against allowlists, including installed framework assemblies. Passing that
check must not be confused with passing the runtime privilege check. Samsung's
[.NET TV FAQ](https://developer.samsung.com/smarttv/develop/faq/tizen-net-tv.html)
also documents restrictions on direct native-library imports and packaged
native libraries. Merely targeting .NET 2.0 does not resolve those restrictions.

A separate manifest mechanism is now supported by a concrete shipped example:
`com.samsung.tv.csfs/tizen-manifest.xml` declares an `app-context-rule` whose
source is `XF86Home` and whose target launches Samsung firstscreen with
`entry_point:smarthub_key`, conditioned on product not being `lfd`. This package
uses the internal `dotnet-inhouse` application type. Its identity, privileges
and application type must not be copied into an independently signed helper.

The context parser's uninstall entry point calls
`context_plugin_parser_remove_db`; the removal code uses app-ID-scoped deletes
from `managed_app`, `key_filter` and `task_filter`. Its notification routine
updates `memory/appfw/app_context_db_change`. This is static evidence of a
cleanup mechanism, not a verified rollback. Acceptance of the manifest section
in an ordinary signed package, invocation of the parser, rule precedence and
behavior after removal remain unverified. In particular, the shipped
`tag_parser_list.txt` does not list `app-context`; this analysis has not resolved
the significance of that omission at this stage; the next follow-up below
resolves it for the newer installer. No rule-bearing package was installed.

The resulting research status is: the managed getter requires an internal
grant; package-declared key rules are a separate unresolved lead; neither
establishes fixed CleanFrame startup. Any future test that registers an actual
Home/startup rule is a native configuration write, even if performed by the
package installer, and still needs the separate authority and exact-value
recovery baseline described above. Private REA outputs, selected firmware
files, disassembly and `dotnet-and-manifest-findings.json` retain the evidence.

### Follow-up: active plugin registry and boot certificate levels

Further offline analysis located the newer installer's actual registry:
`/usr/share/app-installers/plugins_list.txt`. It explicitly registers the
`app-context` tag, flag `0x00040000`, with
`/etc/package-manager/parserlib/libapp-context.so`. In
`libapp-installers.so.1.22.10`, `StepRunParserPlugin::ProcessPlugins` constructs
the plugin manager with that registry, loads plugins and runs them. The missing
entry in the older `tag_parser_list.txt` is therefore not evidence that the
feature is unavailable. This establishes registration and an installer call
path, not successful acceptance of a particular third-party package or Home
rule precedence. No rule-bearing package has been installed.

There is also a concrete signature-dependent boot restriction in
`libtpk-installer.so`. `StepManifestAdjustment::process` checks the privilege
level recorded by `StepCheckSignature::process` in the installer context.
The enum maps 0 to UNTRUSTED, 1 to PUBLIC, 2 to PARTNER and 3 to PLATFORM.
Levels 2 and 3 skip a branch which, for applicable API versions, rewrites
service applications' `on-boot` and `auto-restart` attributes to `false` in
both the XML and parsed application data. This is evidence from the TPK
installer; it must not be represented as a separately verified WGT runtime
test. The latest locally signed CleanFrame widget's distributor certificate
chain contains the Public designation. No private key was opened and no
certificate was replaced during this check.

The [Tizen Web Runtime specification](https://docs.tizen.org/platform/compliance/media/tizen-3.0-wrt-core-spec.pdf)
documents the Partner certificate requirement for a Web Service's `on-boot`.
[Samsung's privileges FAQ](https://developer.samsung.com/smarttv/develop/faq/privileges.html)
explicitly describes a Partner-level distributor certificate bound to the test
device's DUID for testing. Publishing apps that use Partner privileges has a
separate Seller Office partner-group requirement. A Partner test certificate
does not grant the internal Platform privilege used by the managed Vconf API.
The existing author certificate must be retained if updating CleanFrame.

Finally, `app-boot-manager`'s `mgr_util_get_firstscreen_appid` reads
`db/first_screen/type`. Configuration and normal-mode code can schedule this
app through the job manager when their autostart conditions pass; the app-booting
cold-boot path also uses the value as bundle data. This strengthens the link
between the native firstscreen setting and some startup paths, but does not
prove all power-on paths or remove the need for a live recovery baseline.

The next useful device experiment would separate package-rule acceptance from
boot-service execution and from foreground startup. A boot-service test needs
a suitable distributor certificate and must distinguish a full cold boot from
standby resume. A successful service boot alone would not prove that CleanFrame
always becomes the foreground app. These tests have not been performed. All
new files and disassembly are retained in ignored `package-analysis/` under the
firmware investigation directory; the TV and its certificates remain unchanged.

## Cold-boot cleanup mechanism (31 October 2026)

Offline analysis of the extracted 1360.0 firmware identified a specific cleanup
path in Samsung's `BuiltInAppUpgrader.dll`. REA decoded the managed methods and
their string/member references; this was static analysis, not execution on the TV.

`AppUpgrade.OnAppControlReceived` calls `PackageUtils.UninstallDebugPackages`
when its upgrade manager is not yet initialised, its reset state is zero and
the launch extra data is `launch_event=power_on`. The cleanup enumerates packages
with `PACKAGE_REMOVABLE=true` and `PACKAGE_READONLY=false`. For each package,
`IsDebugPackage` first excludes any package containing an application whose type
is exactly `dotnet-inhouse`; otherwise it returns true when the package's
privileges contain `http://tizen.org/privilege/internal/appdebugging`. Matching
packages are passed to `Tizen.Applications.PackageManager.Uninstall`.

This marker is added by installation, not by the C# compiler's Debug/Release
setting. The TV SDB plugin's native `appinstall` command template invokes
`pkgcmd -i ... -q -G`; `pkgcmd` describes `-G` as SDK debug-mode installation.
In `libapp-installers.so.1.22.10`, `StepConfigure.SetupDebugMode` stores
`PkgMgrInterface.GetDebugMode()` in the configuration byte at offset `0x1ac`.
`StepPrivilegeCompatibility.process` tests that byte and appends the internal
`appdebugging` privilege when it is set. The original probe manifest requested
only `appmanager.launch`, so omitting a debug privilege from that manifest had
already been tried implicitly. Changing compiler optimisation or the Partner
certificate does not remove this installation-time marker.

Together, this is a concrete firmware explanation consistent with the observed
post-restart disappearance and Samsung's historical Tizen 4.0 warning. The live
test measured the installed-app inventory, not filesystem deletion or a captured
upgrader log. Restoring the Public device profile before that restart remains
part of the experiment record, but the identified cleanup predicate does not
read that profile or compare Public versus Partner certificates.

The investigated ordinary SDB path has no exposed non-debug install switch.
Installing through the native package-manager API instead would require
`packagemanager.admin`: the firmware D-Bus policy checks this privilege, which
Tizen documents as Platform level. Our issued Partner test certificate is not
a Platform certificate. No equivalent ordinary Partner API path has been verified.

The `dotnet-inhouse` exemption is a concrete **untested** package-level research
lead. It is not evidence that an independently signed package will be accepted,
launched correctly or retained; do not claim that this type universally requires
Platform signing without testing the actual enforcement. Any experiment should
retain the separate probe identity, leave boot/restart disabled, verify normal
uninstallation before a restart, and preserve production CleanFrame. Marking a
test package non-removable is not an appropriate first experiment because it
would undermine the known uninstall recovery path. No type variant, package
database edit, updater disablement or firmware patch was applied in this follow-up.

General boot database repair and `.NET` initialisation scripts were also read.
They do not establish an unconditional purge of every native package. The WAS
app-info comparison removes stale menu records after a package lookup fails;
that is distinct from the explicit uninstall path above.

Private evidence is in
`.local/native-home-investigation/firmware-1360/native-cleanup-analysis/`,
including `builtin-upgrader-rea.json`, `builtin-cleanup-il.txt`,
`builtin-statics.txt`, `installer-debug-privilege.txt` and
`installer-debug-precheck.txt`. This follow-up made no TV connection or change.

Sources: [Samsung's Tizen 4.0 cold-boot warning](https://developer.samsung.com/tizen/blog/en/2019/02/19/launch-your-tizen-net-application-on-samsung-smart-tv)
and [Tizen native privilege levels](https://github.com/Samsung/tizen-docs/blob/master/docs/application/native/reference/security-privileges.md).

### Startup latency investigation (31 October 2026)

The owner reports approximately ten seconds until CleanFrame appears and asks
for an immediate start. The timing reference (Power press versus first TV image)
and the split between service scheduling, runtime startup and UI rendering have
not yet been measured.

Offline inspection of the installed service's source confirms that its
10,000 ms timer is an **exit deadline**, not a launch delay. The AppControl
callback sends the launch request immediately and cancels that timer. Reducing
the deadline would not accelerate that path. The existing compiler configuration
already uses `-optimize+`.

The extracted 1360.0 firmware's AMD configuration specifies
`service_app_onboot_interval=1000`. The on-boot loader at `0x11c18` in
`libamd.so.1.2.17` schedules services using `g_timeout_add`, with offsets derived
from that interval and list position. Its entry point at `0x12ff8` first queues
the loader with `g_idle_add`. This establishes platform-side staggering, not an
exact ten-second delay for this service: the live queue, its trigger time and
the installed configuration have not been read back. This is a global platform
setting, not a timing attribute in our service manifest.

CleanFrame's source startup calls initial rendering directly; fonts and picture
resources load asynchronously. No fixed ten-second startup wait was found there.
Launching from the service's earlier creation callback or replacing its .NET
runtime with a small native executable are untested optimisation candidates;
neither can remove time before the platform schedules the service. The separate
delayed `dotnet-init.service` mainly performs maintenance; its unit placement
alone is not evidence that it blocks this launch.

No TV connection, package update or platform-setting change was made during this
inspection. The working autostart remains installed. A timing comparison is
needed before claiming a speedup; zero-latency startup has not been established.

## Reproduce an unsigned build

1. Copy `nu8000.example.json` to ignored `.local/nu8000.json`.
2. Replace both identity placeholders with the IDs from your own SDK-generated
   project. Keep the identity and author certificate stable for installed updates.
3. Choose installed app identifiers in `selection.home` (one to nine). Dynamic
   entries also need `{ "id": "APP_ID", "appId": "APP_ID", "name": "App name" }`
   in `selection.appRecords`. Keep your personal selection local.
4. From the repository root run `python scripts/prepare_nu8000.py`.

For a private build with your own Pixabay key, add `--with-online-keys` after
configuring `.local/daily-pictures.json` as described in
[daily pictures](daily-pictures.md). The default omits credentials. Both modes
use public fonts. A widget containing a key must stay private.

The builder prints a fresh ignored folder containing `stage/`, an unsigned
widget and `build.json`. It does not connect to the TV, read certificates, sign,
install, or alter Home/startup settings. Public source alone is insufficient to
update another owner's signed installation.

On Windows, the generated `stage` can be signed with the official SDK CLI:

```powershell
& '<SDK>/tools/ide/bin/tizen.bat' package -t wgt -s '<YOUR_PROFILE>' -o '<NEW_SIGNED_OUTPUT>' -- '<PRINTED_STAGE>'
```

Keep the output local. Use the [setup guide](agent-tv-setup-guide.md) for separate
device installation. On this TV the Samsung distributor certificate had to use
the actual SDB certificate DUID; a network API UUID or a manually typed model/IP
was not a substitute. Device Manager's **Permit to install applications** was
also needed. No certificates, identifiers, IPs or signed packages are in this fork.

Run `python scripts/test_nu8000.py` for overlay and package checks. Run the
upstream lint, source, device and public-source checks as documented. The
upstream `check:tools` suite imports POSIX `termios` and cannot run on native
