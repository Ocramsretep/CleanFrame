# Samsung UE49NU8079 adaptation

This page records the **working results** on this fork's Samsung UE49NU8079,
firmware T-KTM2DEUC-1360.0, Tizen 4.0, ARMv7. They do not establish
compatibility with another TV. [TV status](tv-status.md) gives the short current
state; [native wake](native-wake.md) is the runbook for the installed startup
service. Earlier experiments remain in Git history.

## Working app build

The source widget still requests Tizen 6.5. For this TV, the separate
`scripts/prepare_nu8000.py` overlay creates a Tizen 4.0 build using the
owner's existing SDK-generated package and application identity. Ordinary
`npm run package` does not apply that overlay. Keep the existing author
certificate and app identity for updates.

## Current startup state

A separate Partner-signed normal `.NET` service is installed on this TV. It
starts CleanFrame after a full TV restart and after the observed display
transition on short standby/wake, without an always-running computer. The
owner disabled Samsung's “start last app” option. One full boot took more than
ten seconds to show CleanFrame. The service and its exact local recovery
artifacts are described in [native wake](native-wake.md).

This startup service is separate from the Home-button assignment below. The
physical Home button **currently opens CleanFrame**.

## Temporary physical Home mapping

On 1 November 2026, the owner approved a temporary Home test on this exact
TV. Two separate, Partner-signed TPKs made physical Home open CleanFrame:

1. A boot-disabled registration TPK declared a root-level
   `<app-context appid="CLEANFRAME_FULL_APP_ID"/>` with **no** key rule and
   no `ui-type` attribute. Its package and service app IDs were separate from
   CleanFrame and from the rule and database-reader packages.
2. A boot-disabled rule TPK declared `XF86Home`, `override=true`,
   `product!=lfd`, `request=launch`, and a target containing CleanFrame's
   **full application ID**, including the suffix after its package ID. The
   relevant manifest element was:

```xml
<app-context appid="OWN_RULE_APP_ID" ui-type="partial">
  <app-context-rule>
    <source selector="key" override="true">XF86Home</source>
    <condition selector="product" operator="not">lfd</condition>
    <target selector="app" request="launch">CLEANFRAME_FULL_APP_ID</target>
  </app-context-rule>
</app-context>
```

The firmware parser stored the target as
`package:<CleanFrame full application ID>`. Static inspection showed that the
`package:` selector compares this value with the managed task's complete app
ID. Using only CleanFrame's ten-character package ID did not work. On this TV,
the physical Play/Pause control also opened CleanFrame only when **both** the
registration and full-ID rule were installed; either change alone failed.

### Observed result and rollback

Before installation, the test saved an exact copy of the active
`/opt/dbspace/.app-context.db` table rows and the installed-app ID set. The
Samsung installer added one CleanFrame `managed_app` row for the registration
TPK and one `managed_app` plus one `key_filter` row for the Home-rule TPK.
Every original `managed_app`, `key_filter` and `task_filter` row remained
unchanged. Public developer installation permission was restored before the
physical test.

From another screen, one Home press opened CleanFrame and left it visible.
The owner then performed a full restart through the Samsung logo. Both packages
and exact added database rows survived; Home again opened CleanFrame from
another screen. A short Power off/on after about 20 seconds in standby gave
the same visible Home result. One reboot and one short standby cycle were
tested; this is not a long-term survival test.

For the temporary rollback test, the Home-rule TPK was uninstalled **before** the registration TPK. A fresh
database capture matched every original table row and the original app-ID
inventory; Public developer permission was restored. The owner confirmed
that Home again opened Samsung Home and CleanFrame opened normally. **Neither
Home-test package remained installed after that test.** The CleanFrame widget, native
Vconf Home setting and firmware were not changed.

### Current assignment

On 1 November 2026, the owner requested the Home assignment. The same two
verified signed packages were installed again after capturing a **new** exact
database and app-inventory baseline. The controller verified that the
registration added one `managed_app` row, then the rule added one
`managed_app` and one `XF86Home` `key_filter` row; all original rows stayed
unchanged. Public developer installation permission was restored. A second
read confirmed that both packages and the exact expected rows were present.
The owner pressed Home from another screen and saw CleanFrame open and remain.
At first, Samsung Home seemed to begin appearing briefly before CleanFrame
took over. In the latest owner checks after the web-widget updates, no such
flash was visible, including after a full restart. The cause of the earlier
effect and its disappearance has not been measured. The earlier reboot and
standby observations apply to the same packages. After a later full
Samsung-logo restart of the current installation, the owner again confirmed
that physical Home opened
CleanFrame from another app. A short standby cycle with the current installation
has not been separately checked.

The private controller retains the current baseline in
`.local/native-home-investigation/managed-cleanframe-registration/live-test-state.json`.
To restore the original Home behavior on this reference TV, keep CleanFrame
installed and run `python .local/native-home-investigation/run-home-fullid-registration.py cleanup`
with the TV reachable. It removes the rule package **first**, then the
registration package, restores Public permission and compares the exact
database rows and app inventory with that fresh baseline. Confirm physically
that Home opens Samsung Home afterward. Preserve the baseline file until the
rollback has been verified. The installed native startup service is separate
and is not removed by this cleanup.

### Repeating this on the reference TV

The exact signed TPKs, certificate profile, device-specific IDs, saved Public
permission file, database captures and test controller are private under
ignored `.local/`. On this workstation the relevant files are:

- `.local/native-home-investigation/managed-cleanframe-registration/status.json`
- `.local/native-home-investigation/home-fullid-rule/status.json`
- `.local/native-home-investigation/run-home-fullid-registration.py`
- `.local/native-home-investigation/run-runtime-db-probe-multi.py`
- `.local/native-wake.json`

Those files are reference-machine artifacts, not a public unattended
installer. A future agent should validate the target model, firmware, package
hashes, three distinct test/read package identities and current app inventory;
capture a **fresh** active-database baseline; then use the controller's
`register`, `install-rule`, `verify` and `cleanup` phases with the owner's
visible checks. Installation uses the device's Partner permission and restores
its saved Public file. The Public file is a locally retained recovery copy,
not a fresh readback from the TV. If an installation or read fails, check the
actual inventory and database before proceeding. Do not leave a Home rule
pointing to a missing app. No Home or startup Vconf write is part of this path.

A long-running Home installation, operation across firmware updates and behavior
from every Samsung screen remain unverified. Native Home work needs a separate
device task, the owner's authority and exact rollback values for anything it
would change.

## Other approaches, briefly

- Home and Play/Pause rules targeting only CleanFrame's package ID were
  registered but did not open CleanFrame, including after a reboot. The
  Browser control worked because its package ID and app ID are identical.
- A managed-app registration alone, a full-ID rule alone, and a registration
  with `ui-type=partial` plus the old package-ID target did not open
  CleanFrame. Timeshift was left enabled; the successful Browser and
  full-ID CleanFrame tests show it is not a blanket key blocker.
- The upstream LS03D one-shot Home helper was not applied to this TV. Tested
  managed Vconf getters lacked the required internal privilege, so exact
  native Vconf Home recovery values remain unavailable.
- The first native `dotnet-inhouse` service survived a restart but could not
  launch CleanFrame. The working startup service uses a normal `dotnet`
  package installed through the tested alternate path instead.
- The rectangle-plus remote button produced no CleanFrame DOM key event in
  the bounded check. The combined color/number control prevented a direct
  red-button test. No shortcut is retained from those experiments.
- Firmware extraction and offline parser analysis informed these tests.
  Firmware installation or modification was not attempted.

## Reproduce an unsigned app build

1. Copy `nu8000.example.json` to ignored `.local/nu8000.json`.
2. Replace both identity placeholders with the IDs from your own SDK-generated
   project. Keep that identity and author certificate stable for updates.
3. Choose installed app identifiers in `selection.home` (one to nine).
   Dynamic entries also need
   `{ "id": "APP_ID", "appId": "APP_ID", "name": "App name" }` in
   `selection.appRecords`. Keep personal selection local.
4. From the repository root run `python scripts/prepare_nu8000.py`.

For a private build with a Pixabay key, add `--with-online-keys` after
configuring ignored `.local/daily-pictures.json` as described in
[daily pictures](daily-pictures.md). The default omits credentials. Both modes
use public fonts; a widget containing a key must stay private.

The builder prints a fresh ignored folder containing `stage/`, an unsigned
widget and `build.json`. It does not connect to the TV, sign, install or
alter Home/startup settings. On Windows, the generated stage can be signed
with the official SDK CLI:

```powershell
& '<SDK>/tools/ide/bin/tizen.bat' package -t wgt -s '<YOUR_PROFILE>' -o '<NEW_SIGNED_OUTPUT>' -- '<PRINTED_STAGE>'
```

Keep signed output local. See the [setup guide](agent-tv-setup-guide.md) for
separate device installation. On this TV the Partner certificate had to use
the actual SDB certificate DUID, and Device Manager's **Permit to install
applications** step was needed.

## Guided reference-TV setup

`scripts/setup_nu8000.py` coordinates the existing private reference-TV
steps. It is **not** a portable or unattended installer. It requires the
owner's ignored `.local/nu8000.json`, `.local/native-wake.json`, exact tested
startup TPK, Partner/Public device profiles and the private Home controller.
Copy `setup-nu8000.example.json` to ignored `.local/setup-nu8000.json` and
select the existing **web app** signing profile there. For an app update,
include the previously installed signed widget path and its SHA-256; the
builder compares both author and distributor certificates with the fresh
widget. The startup service can use a separate Partner signing profile.
It checks that identities, package hashes, TV model and Tizen capability match
before a device change. Only the explicit `update-app` / `restore-app` actions
replace an installed widget; the installed startup service is not replaced.

Run commands individually from the repository root:

```text
python scripts/setup_nu8000.py plan
python scripts/setup_nu8000.py build-app
python scripts/setup_nu8000.py build-startup
python scripts/setup_nu8000.py install-app --apply
python scripts/setup_nu8000.py update-app --apply
python scripts/setup_nu8000.py restore-app --apply
python scripts/setup_nu8000.py launch-app --apply
python scripts/setup_nu8000.py install-startup --apply
python scripts/setup_nu8000.py assign-home --apply
python scripts/setup_nu8000.py verify-home --apply
python scripts/setup_nu8000.py restore-home --apply
```

`build-app` creates a fresh NU8000 overlay, signs it through Samsung's SDK,
checks the signed identity and retains its path and hash in ignored
`.local/setup-nu8000-state.json`. Add `--with-online-keys` only for a private
build. `build-startup` rebuilds and signs into ignored `dist/`; it does **not**
replace the exact owner-tested startup TPK used by `install-startup`. Both
build steps are offline. An app or service already in the TV app inventory is
reported and left untouched by `install-app` / `install-startup`. For an app
update, `update-app` requires the exact previously installed signed widget in
the private setup configuration and compares both signing certificates. It
verifies the active Home database before and after the in-place update without
removing the Home packages. `restore-app` reinstalls that exact prior widget.

Every TV action needs `--apply`. Without it, the command only prints that the
step is prepared and makes no TV connection. `assign-home` calls the private
controller's `register`, `install-rule` and `verify` phases; if those fail it
attempts `cleanup` and retains private logs. If Home is already assigned, it
only verifies the active packages and database rows. `restore-home` removes
the rule before the registration and compares database/app inventory with the
saved baseline. The owner must confirm visible Home and CleanFrame behavior
after assignment or restore. No script can infer that from an SDB success code.

On Windows, the signing and Docker build may require normal SDK/Docker access
outside Codex's filesystem sandbox. The script keeps outputs and logs under
ignored `.local/` or `dist/` and does not publish certificates or packages.
